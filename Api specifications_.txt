Complete API Specification

Developer Intelligence Extension

Document Version: 1.0
API Version: v1
Protocol: HTTPS
API Style: RESTful
Data Format: JSON
Backend: Python + FastAPI
Authentication: JWT / OAuth 2.0-compatible token flow
Primary Database: PostgreSQL
Cache / Queue: Redis
Vector Search: pgvector / Vector Database
Client: VS Code Extension using TypeScript

---

1. API Purpose

The API layer is the communication backbone between the IDE extension and the Developer Intelligence backend.

It allows the extension to:

- Analyze source code
- Detect coding issues
- Identify root causes
- Generate fixes
- Validate generated fixes
- Analyze database queries
- Recommend indexes and query optimizations
- Run security scans
- Detect vulnerabilities and secrets
- Validate deployment readiness
- Retrieve reports
- Submit developer feedback
- Retrieve historical intelligence

The API is designed around a hybrid architecture:

Developer
    │
    ▼
IDE Extension
    │
    │ HTTPS / JSON
    ▼
API Gateway
    │
    ├── Authentication
    ├── Authorization
    ├── Validation
    ├── Rate Limiting
    └── Routing
          │
          ├── Code Intelligence
          ├── Database Intelligence
          ├── Security Intelligence
          ├── Deployment Intelligence
          └── AI/ML Services
                    │
                    ▼
            Validation Engine
                    │
                    ▼
              Data Layer

2. Base URL

Development

http://localhost:8000/api/v1

Production

https://api.<domain>/api/v1

All production communication must use TLS/HTTPS.

---

3. API Design Principles

The API follows these principles:

Stateless Requests

Each request contains enough information for the server to process it without relying on server-side session state.

Resource-Oriented URLs

Example:

/projects
/analysis/code
/security/scans
/deployment/validations

Versioning

/api/v1/...

JSON Communication

Request and response bodies use JSON unless otherwise specified.

Asynchronous Processing

Long-running operations return a job ID instead of keeping the HTTP connection open.

---

4. Standard HTTP Headers

Every authenticated request should contain:

Authorization: Bearer <access_token>
Content-Type: application/json
Accept: application/json
X-Request-ID: <uuid>
X-Client-Version: 1.0.0
X-Extension-Version: 1.0.0

Optional:

X-Project-ID: proj_xxxxx

---

5. Standard Response Envelope

Successful response:

{
  "success": true,
  "data": {},
  "error": null,
  "request_id": "req_123456"
}

Failure response:

{
  "success": false,
  "data": null,
  "error": {
    "code": "INVALID_REQUEST",
    "message": "The submitted request is invalid.",
    "details": {}
  },
  "request_id": "req_123456"
}

40. Deployment Decision Model

The API uses three main decisions:

READY
REVIEW
BLOCKED

READY

No blocking issues detected.

REVIEW

Non-critical warnings require developer review.

BLOCKED

At least one release-blocking condition exists.

Example:

{
  "decision": "blocked",
  "blocking_issues": [
    {
      "category": "security",
      "severity": "critical",
      "message": "Critical security vulnerability detected."
    }
  ]
}

500 → Internal server error

Rate limits should differ by operation cost.

Example initial configuration:

Normal API:
100 requests/minute

60 requests/minute

Security Scan:
10 requests/hour

Project Scan:

Response:

429 Too Many Requests

57. Request Size Limits

To prevent excessive payloads:

Single code request       → configurable limit
Project metadata          → small
Large repository analysis → asynchronous upload/job

Large files should be chunked or processed locally rather than placed directly into ordinary API requests.

The database-analysis API should support two modes.

Mode A — Static

Developer sends:

Query
Schema
Execution Plan
Statistics

No direct database credentials are required.

Mode B — Controlled Connection

The backend or local agent connects to the database using temporary, least-privileged credentials.

Credentials should:

- Never be logged
- Never be stored permanently unless explicitly required
- Be encrypted in transit
- Be scoped only to required operations

83. Final API Design Philosophy

The API should enforce a strict separation between:

Detection
    ↓
Analysis
    ↓
AI Recommendation
    ↓
Validation
    ↓
Developer Approval
    ↓
Application

The most important design principle for the project is:

AI generates recommendations; deterministic engines and validation mechanisms establish whether those recommendations are safe and useful.

This makes the Developer Intelligence Extension more reliable than an ordinary AI code assistant and directly supports the project's three core capabilities:

SELF-CORRECTING CODE
        +
DATABASE PERFORMANCE OPTIMIZATION
        +
DEPLOYMENT SECURITY & VALIDATION
