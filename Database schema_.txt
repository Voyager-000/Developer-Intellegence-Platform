DETAILED DATABASE SCHEMA

Developer Intelligence Extension

Database Technology

Primary Database: PostgreSQL
Cache: Redis
Vector Storage: pgvector / Vector Database
Object Storage: S3-compatible storage for large reports and artifacts

The PostgreSQL database is the primary source of truth for structured application data.

---

1. DATABASE ARCHITECTURE

The database is organized into the following logical domains:

1. User and Access Management
2. Project and Repository Management
3. Code Analysis
4. Self-Correction
5. Database Performance
6. Security Analysis
7. Deployment Validation
8. AI and Knowledge Management
9. Feedback and Analytics

3. USERS TABLE

Table: users

Purpose:
Stores developer accounts and authentication-related metadata.

Columns:

id

- Type: UUID
- Primary Key
- Description: Unique user identifier

email

- Type: VARCHAR(255)
- Unique
- Not Null
- Description: User email address

name

- Type: VARCHAR(100)
- Not Null
- Description: Display name

password_hash

- Type: TEXT
- Nullable if external authentication is used
- Description: Secure password hash

role

- Type: ENUM
- Values: developer, project_owner, admin

status

- Type: ENUM
- Values: active, suspended, deleted

created_at

- Type: TIMESTAMP WITH TIME ZONE

updated_at

- Type: TIMESTAMP WITH TIME ZONE

last_login_at

- Type: TIMESTAMP WITH TIME ZONE
- Nullable

Recommended indexes:

UNIQUE(email)
INDEX(role)
INDEX(status)

37. PRIMARY RELATIONSHIPS

USER → PROJECT

One user can own multiple projects.

users.id
↓
projects.owner_id

PROJECT → REPOSITORY

One project can have one or multiple repositories.

projects.id
↓
repositories.project_id

PROJECT → ANALYSIS JOB

One project can have many analysis jobs.

projects.id
↓
analysis_jobs.project_id

ANALYSIS JOB → FINDINGS

One analysis job can generate many findings.

analysis_jobs.id
↓
findings.analysis_job_id

FINDING → FIX

One finding can have multiple candidate fixes.

findings.id
↓
fixes.finding_id

FIX → VALIDATION

One fix can have multiple validation attempts.

fixes.id
↓
fix_validations.fix_id

DATABASE ANALYSIS → DATABASE FINDINGS

database_analyses.id
↓
database_findings.database_analysis_id

DATABASE ANALYSIS → RECOMMENDATIONS

database_analyses.id
↓
database_recommendations.database_analysis_id

SECURITY SCAN → SECURITY FINDINGS

security_scans.id
↓
security_findings.security_scan_id

DEPLOYMENT VALIDATION → DEPLOYMENT CHECKS

deployment_validations.id
↓
deployment_checks.deployment_validation_id

PROJECT → FEEDBACK

projects.id
↓
feedback.project_id

43. DATABASE SECURITY

PostgreSQL should implement:

• TLS connections
• Encryption at rest where supported
• Least-privilege database users
• Separate application and administrative roles
• Prepared statements
• Parameterized queries
• Database backups
• Access logging
• Migration versioning

Credentials must be stored outside the source code.

53. DATABASE DESIGN OBJECTIVE

The database is designed to provide:

1. Traceability
   Every recommendation can be traced back to the project, commit, analysis, and finding that generated it.

2. Reliability
   Validation results are stored separately from AI-generated recommendations.

3. Security
   Secrets and sensitive source code are not unnecessarily persisted.

4. Scalability
   Heavy operations use asynchronous jobs and Redis-backed workers while PostgreSQL remains the structured source of truth.

5. Intelligence
   Historical findings, fixes, feedback, and knowledge patterns can be reused by the AI and recommendation engines.

6. Explainability
   The platform can explain how a final recommendation was generated and validated.

The resulting database architecture supports the complete Developer Intelligence workflow:

CODE
→ ANALYZE
→ DETECT
→ FIX
→ VALIDATE
→ OPTIMIZE
→ SECURE
→ TEST
→ DEPLOY
→ LEARN
